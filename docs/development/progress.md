# Forge Progress

Persistent record of completed milestones/phases, per `docs/development/roadmap.md`.

This is a concise historical record, not a full implementation log. Each
entry summarizes what changed and why; exact test counts, file-by-file test
lists, and hardware-verification boilerplate have been omitted deliberately
(every milestone since M8 was hardware-verified on the project's reference
940MX unless the entry says otherwise). For full technical rationale behind
a specific decision, see the referenced `docs/architecture/*.md` file, ADR,
or (where one still exists) the milestone's own `docs/development/mXX-*.md`
report.

## Phase 1 — Core Foundations

### M1 — Tensor abstraction and CPU execution boundary
`Tensor` (shape/dtype/device), `DType`, `Device`, the `Backend`/`CPUBackend` dispatch boundary, and Forge-specific errors (`ShapeMismatchError`, `UnsupportedDTypeError`, `UnsupportedDeviceError`). Operations: `+`, `-`, `*` (broadcasting), `@` (1D/2D matmul), `.sum()`, `.reshape()`.

### M2 — Automatic differentiation core
Reverse-mode autograd on top of the M1 Tensor: `requires_grad`, `.grad`, `.is_leaf`, `.grad_fn`, `.backward()`, `.zero_grad()`. New `forge/autograd/` package (`Node` graph nodes, topological `run_backward`, broadcast/matmul/sum backward math). Backward rules for all M1 operations, with broadcast-aware gradient reduction and gradient accumulation across multiple use sites. Graph is freed as it is consumed by `backward()`. See `docs/architecture/autograd.md`.

### M3 — Module and parameter system
Neural-network composition on top of the Tensor+autograd stack: new `forge/nn/` package (`Parameter`, a `requires_grad=True`-by-default `Tensor` subclass; `Module`, with attribute-based parameter/child-module registration, recursive `parameters()`/`named_parameters()` discovery, `train()`/`eval()` mode propagation) and `Linear`/`ReLU`. New `Tensor.relu()` primitive following the Tensor->Backend->autograd `Node` pattern. New minimal `forge/random.py` (a process-global generator) for deterministic `Linear` init. See `docs/architecture/modules.md`.

### M4 — Losses and optimizer
`forge/nn/loss.py` (`MSELoss`, `CrossEntropyLoss`) and `forge/optim/` (`SGD`). New `Tensor.exp()`/`.log()` primitives, needed for a numerically stable `CrossEntropyLoss` (log-sum-exp trick). `SGD.step()` mutates `Parameter._data` in place via NumPy, so it never attaches a `grad_fn` or extends the autograd graph. See `docs/architecture/optimization.md`.

### M5 — Dataset, DataLoader, and transforms
Data pipeline foundation, independent of `Module`/`Loss`/`Optimizer`/a training engine: new `forge/data/` package (`Dataset`, `TensorDataset`, `Subset`, `random_split`), `DataLoader` (batching, deterministic shuffling, `drop_last`), and a composable transform set (`Transform`, `Compose`, `ToTensor`, `Normalize`, `Reshape`, `Flatten`, `Lambda`). `TensorDataset` wires `transform`/`target_transform` separately, so a feature transform cannot silently reach a label. Batches are always Forge `Tensor`s. See `docs/architecture/data-system.md`.

## Phase 2 — Training Framework

### M6 — Training engine
Forge's first training engine: new `forge/training/` package (`Trainer`, `TrainingHistory`, `EpochResult`, `EvaluationResult`, and a `Metric` abstraction with `MeanSquaredError`/`MeanAbsoluteError`/`Accuracy`). `Trainer` orchestrates the existing components -- it computes no gradients and implements no loss/optimizer/batching logic itself. New `forge.no_grad()`, used by `Trainer.evaluate()` so an evaluation forward pass builds no autograd graph. Metrics aggregate by accumulating running sums/counts across batches, not per-batch mean averaging, so unequal batch sizes are weighted correctly. See `docs/architecture/training-engine.md`.

### M7 — Model persistence
New `forge/serialization/` package (`save_model`, `load_model`, `register_module`). A model file is a ZIP archive (`metadata.json` + one `.npy` per parameter) -- structured, versioned (`forge_format_version`), and inspectable without Forge; loading never executes code found in the file. Architecture reconstruction goes through an explicit in-process registry keyed by a plain string type name -- never pickle, `eval`, or dynamic import (see ADR-003); a custom `Module` subclass must call `register_module()` before it can be saved or loaded. No autograd graph or optimizer state is ever saved. Saving is atomic (temp file + `os.replace`). See `docs/architecture/persistence.md` and `docs/architecture/decisions/ADR-003-persistence-format.md`.

## Phase 4 — GPU/CUDA (reordered ahead of Phase 3, Data & Model Ecosystem)

### M8 — Initial CUDA backend
Forge's first real CUDA execution backend: new `forge/backend/cuda/` package (`kernels.cu`, `build.py` -- locates `nvcc`/MSVC and compiles lazily on first CUDA use, `backend.py` -- `CUDAStorage`/`CUDABackend`). Kernels compiled with `nvcc -arch=sm_50`, loaded via the standard-library `ctypes` -- no PyTorch/TensorFlow/CuPy/JAX dependency, per ADR-004. Deliberately small forward-only operation set: transfer, `add`/`sub`/`mul` (exact-shape only), `matmul` (naive one-thread-per-output), `sum` (full reduction only), `reshape`. CUDA autograd explicitly out of scope: `Tensor.backward()` raises `UnsupportedDeviceError` for any non-CPU differentiable operation. Verified on the reference 940MX; all CUDA tests skip cleanly with the CUDA toolchain removed from `PATH`. See `docs/architecture/cuda-backend.md` and `docs/architecture/decisions/ADR-004-cuda-execution-strategy.md`.

### M9 — CUDA Module execution and device movement
Extends the CUDA backend to high-level `nn.Module` execution: `Module.to(device)` recursively moves every `Parameter` in a module tree via a new private in-place `Tensor._move_storage_()`. Closed two kernel gaps blocking `Linear -> ReLU -> Linear` on CUDA: a real `relu` kernel, and a targeted row-broadcast addition to `add`/`sub`/`mul` supporting exactly `(rows, cols) + (cols,)` (a batched `Linear`'s bias add) -- general N-D broadcasting remained out of scope. A CUDA forward pass had to run inside `forge.no_grad()` (backward on a CUDA-resident output still raised `UnsupportedDeviceError`). `Trainer`, losses, and persistence remained CPU-only. See `docs/architecture/cuda-backend.md` and `docs/architecture/modules.md`.

### M10 — CUDA autograd
Extends the CUDA backend from forward-only to full reverse-mode autograd -- a CUDA graph now builds and differentiates entirely on the GPU, including a CUDA-executing `SGD.step()`, with no CPU fallback. Backward computation became backend-aware rather than a second autograd engine: seven new `Backend` ABC methods (`add_backward`, `sub_backward`, `mul_backward`, `matmul_backward`, `sum_backward`, `reshape_backward`, `relu_backward`) plus `sgd_step`, implemented once in `CPUBackend` (relocated from the now-deleted `forge/autograd/functions.py`) and once in `CUDABackend` (real kernels, composed with existing forward kernels wherever the math allows). `forge/autograd/engine.py`'s graph-traversal logic needed no device-specific changes beyond dispatching multi-consumer gradient accumulation through `Backend.add()`. See ADR-005 and `docs/architecture/{autograd,cuda-backend}.md`.

## Phase 5 — Performance

### M11 — Performance benchmarking and targeted optimization
Adds a reproducible benchmark subsystem and applies one measurement-justified optimization: a new top-level `benchmarks/` package (CPU/CUDA-aware timing with explicit `cudaDeviceSynchronize()` bracketing, since async kernel launches make naive `perf_counter()` wrapping measure launch overhead, not execution time), deliberately kept outside `forge` (`import forge` never touches it) and outside the correctness suite. Benchmarking at three scales found M8's naive CUDA `matmul` kernel was a real, measured bottleneck at the 512x512 scale specifically (~4.4x slower than CPU forward). `k_matmul` was rewritten as a standard 16x16-tile shared-memory GEMM (cuBLAS considered and deliberately not introduced, per ADR-004's "no new numerical-library dependency" rationale); the exported kernel signature was unchanged, so no Python-side code changed. Measured ~1.7-1.8x speedup for both forward and backward matmul at 512x512; CUDA matmul remained slower than CPU at this scale even after the optimization, reported as a measured fact rather than hidden. See `docs/performance/benchmarking.md`.

## Phase 4 — GPU/CUDA (continued after Phase 5 — Performance)

### M12 — CUDA Trainer and loss integration
Extends `Trainer` to run a real end-to-end training/evaluation workflow on CUDA through the existing high-level abstractions. `Trainer.__init__` now accepts `device="cuda"`. `Trainer` chose a **validate, never move** model-placement policy: `_check_model_device()` compares `model.device` against `self.device` and raises `UnsupportedDeviceError` naming the required `model.to(device)` call, rather than silently relocating the model. A new `Trainer._to_device_batch()` explicitly transfers each batch immediately before the forward pass -- the only place a batch crosses a device boundary; `DataLoader`/`Dataset` gained no device awareness. `MSELoss` needed zero new CUDA kernels (composes only already-CUDA-capable ops); `CrossEntropyLoss` was deliberately deferred to CPU-only -- it needs `.exp()`/`.log()` and an axis-wise `.sum()`, judged out of proportion to this milestone's core objective. See `docs/architecture/training-engine.md`'s Device semantics section and `docs/architecture/cuda-backend.md`'s CUDA losses section.

### M13 — CUDA model persistence
Extends `save_model`/`load_model` so models with CUDA-resident `Parameter`s can be saved and reloaded -- same ZIP format, `FORMAT_VERSION` unchanged (see ADR-003's Milestone-13 update). `save_model()` copies every `Parameter`'s values to host memory via `Backend.to_numpy()` before writing (a persistence *transfer*, never a computation). `load_model()` gained an optional `device=` kwarg and a device-availability policy: by default it restores onto the archive's recorded device only if that device is available right now (a `"cuda"`-recorded file with no CUDA backend raises a clear `PersistenceError` rather than silently falling back to CPU); an explicit `device=` performs a deliberate conversion in either direction. See `docs/architecture/persistence.md`'s Device semantics section and `docs/architecture/cuda-backend.md`'s CUDA model persistence section.

### M14 — CUDA CrossEntropyLoss
Completes CUDA support for Forge's basic supervised classification workflow, closing the CPU-only limitation deliberately deferred at M12. Four CUDA primitives were added because the loss's own math genuinely needed them: (1) real `exp`/`log` kernels + backward, superseding M8's "unsupported" stubs; (2) `sum(axis=1)` on a 2D tensor (deliberately not general N-D axis reduction); (3) a column-broadcast `sub` kernel (`(rows, cols)` combined with `(rows, 1)`, the transpose of M9's row-broadcast case), needed because both `logits - max` and `shifted - log_sum_exp` have this shape; (4) a non-public `max_axis1` backend method for the log-sum-exp numerical-stability shift (no public `Tensor.max()` was added). `CrossEntropyLoss.forward()` itself needed no rewrite -- once the four primitives existed, the same Tensor-level code already ran correctly on CUDA. See `docs/architecture/cuda-backend.md`'s CUDA CrossEntropyLoss section.

### M15 — Conv2d and MaxPool2d
Expands Forge's neural-network expressiveness beyond dense layers: `nn.Conv2d` (2D cross-correlation, NCHW, integer stride/padding, optional bias) and `nn.MaxPool2d`, both following the M10 Tensor->Backend pattern (`conv2d`/`conv2d_backward`/`max_pool2d`/`max_pool2d_backward`, implemented once per backend, no CUDA-specific code inside `nn/conv.py`/`nn/pooling.py`). **CPU** is im2col-style: `sliding_window_view` builds a zero-copy strided window view, reduced with one big batched matmul (real BLAS). **CUDA** is deliberately *not* the CPU's im2col-plus-matmul approach -- per the brief's "start with a straightforward correct kernel, do not immediately implement cuDNN/cuBLAS/Winograd/FFT/autotuning" constraint, every kernel is one thread per output/gradient-target element, looping over the kernel window in registers; `max_pool2d` backward `atomicAdd`s into a zeroed gradient buffer, the one place atomics were necessary since overlapping pooling windows can target the same input element. Both backends' argmax tie-break conventions (first-occurrence, row-major scan order) agree by construction, verified by test. See `docs/architecture/cuda-backend.md`'s CUDA Conv2d/MaxPool2d section.

### M16 — Sequential, Flatten, and Dropout
Added `nn.Sequential` (ordered container, children register by index so existing traversal/`train()`/`eval()`/`Module.to()` work with no overrides), `nn.Flatten` (dim-range collapse via `reshape`, no parameters), and `nn.Dropout` (inverted-dropout mask via a new `Backend.dropout_mask()`; CUDA generates the mask on-device from one host-drawn seed via a stateless SplitMix64 hash, deliberately avoiding a curand dependency). `Dropout.forward()` re-fetches `forge.random.default_generator()` on every call so one global seed governs a whole run. Persistence needed one accommodation: `Sequential`'s child count is runtime data, not config, so its registered `from_config` builds placeholder children from an explicit `n_children` field before the generic attach loop overwrites them. See `docs/architecture/modules.md` and `docs/architecture/cuda-backend.md`.

### M17 — Adam optimizer and optimizer state
Added `Adam` (`forge/optim/adam.py`) -- original-paper L2-in-gradient weight decay, not AdamW's decoupled decay (deliberate, AdamW out of scope) -- and one new backend primitive, `Backend.adam_step`, following the same `Tensor -> Backend` boundary every op already uses. `Adam.state` maps `Parameter -> state` by Python object identity (not name), so state follows a parameter regardless of which module/attribute currently holds it, and is allocated lazily on first `step()`. `Module.to(device)` moves parameter storage with no optimizer awareness, so Adam does not auto-migrate `m`/`v` across devices -- `step()` raises `OptimizerError` on a device mismatch rather than silently pairing mismatched buffers. Optimizer state lives entirely outside the `Module` tree, so `save_model()` never sees it. See `docs/architecture/optimization.md` and `docs/architecture/cuda-backend.md`.

### M19 — Forge command-line interface
Added `forge`/`python -m forge` (`forge/cli/`: `main.py` dispatch tree, `model`/`checkpoint` `inspect`/`convert`, a `benchmark` passthrough), kept entirely out of `import forge`. `model inspect`/`checkpoint inspect` deliberately never call `load_model()`/`load_checkpoint()` -- they read `metadata.json` directly, because `load_checkpoint()`'s documented contract overwrites `forge.random`'s global RNG state (incompatible with a read-only inspect command), inspection must work on a CPU-only machine regardless of a CUDA-recorded archive, and it must not require the saved types to be registered in-process. `model convert`/`checkpoint convert`, not being read-only, call the real load/save functions directly and inherit that RNG side effect as expected behavior. `forge benchmark` forwards unparsed arguments to `benchmarks.run.main()`. `main.py` catches `CLIError`/`ForgeError` uniformly (prints `Error: ...`, exit 1, no traceback); unexpected exceptions still propagate with a full traceback. See `docs/development/cli.md`.

## Phase 9 — Validation & Release

### M20 — End-to-end MNIST example and validation suite
First realistic integration workload, not a new framework feature: `examples/mnist/` (IDX-format dataset parser + downloader, a small CNN built from existing `forge.nn` layers, a `train.py` CLI with `--resume`). Hardware-verified end to end on CPU and the 940MX with matching accuracy at the same seed and CUDA running ~1.5-1.7x CPU throughput on this small architecture -- a real but modest, unturned speedup, reported as observed. Integration tests use a fast synthetic stand-in dataset, including a resume-equivalence test.

### M21 — Performance profiling and targeted CUDA optimization
Extended the benchmark subsystem to Forge's full current op set. Bottleneck found: the MNIST profile showed CUDA `conv2d` backward dominating the backward phase, narrowed to `k_conv2d_backward_weight`/`_bias`, where at small layer shapes a handful of threads serially summed a large reduction while most of the GPU sat idle. `MaxPool2d`, elementwise ops, `Adam`, and transfers were measured and found *not* to justify optimization at this workload's scale -- left unchanged. Fix: both kernels rewritten as a block-per-output-element shared-memory tree reduction, dispatching per-call between the new kernel and the original M15 one-thread-per-weight kernel based on a measured element-count threshold (a single strategy was not uniformly better across the CNN's two layer shapes). Measured: isolated `conv2d_backward` ~3.4-3.5x faster; end-to-end CUDA MNIST throughput ~1.37x. See `docs/architecture/cuda-backend.md`'s Milestone 21 section and `docs/performance/benchmarking.md`.

### M22 — CUDA memory statistics and allocation lifecycle
Established observable CUDA memory accounting -- explicitly not a caching allocator. New `forge/backend/cuda/memory.py` instruments existing `cudaMalloc`/`cudaFree` call sites; public API via `forge.cuda.memory_stats()`/`reset_peak_memory_stats()`. Two findings, documented not fixed: (1) on the 940MX, a sufficiently large failed `cudaMalloc` leaves the CUDA context unable to launch any further kernel for the rest of the process -- a real driver quirk, so the triggering test runs in an isolated subprocess; (2) Forge's Tensor/autograd/Module/Optimizer object graph contains genuine Python reference cycles, so `CUDAStorage` release is not purely deterministic-refcounting -- an explicit `gc.collect()` is needed before a memory snapshot means "true live allocation." See `docs/architecture/cuda-backend.md`'s CUDA Memory Statistics section.

### M23 — Tensor/autograd reference-cycle audit and fix
Root-caused and fixed the M22-discovered reference-cycle finding. The Tensor/Node ownership graph itself was confirmed acyclic by design. The actual cycle: `forge/autograd/engine.py`'s `_topological_order` used a recursive nested `visit()` closure that referenced itself, a genuine self-referential cycle uncollectible by plain refcounting, keeping the entire per-call topological-order list alive until the next `gc.collect()`. Fix: rewritten as an iterative, explicit-stack post-order traversal with no nested function, verified byte-for-byte identical ordering to the old version. A separate, out-of-scope finding was documented but not fixed: CPython's `_ctypes` extension leaves a small cyclic-garbage pair per certain foreign-function calls through the CUDA backend, confirmed never to retain CUDA device memory. See `docs/architecture/autograd.md`'s Graph teardown and object lifetime section.

### M24 — CUDA memory allocation profiling and caching-allocator design
Measured whether Forge's direct `cudaMalloc`-per-`CUDAStorage` model is a real bottleneck and produced a measurement-backed caching-allocator design -- without implementing one. New `forge/backend/cuda/profiler.py`. Measured on the 940MX (MNIST CNN, steady state): true persistent memory a small fraction of peak; only 14 distinct allocation sizes across a whole trace, 99.1% of allocated bytes an exact-size repeat of one seen earlier -- an offline exact-size cache simulation would reduce ~1,920 real `cudaMalloc`/`cudaFree` pairs to 42 driver calls. Direct timing showed `cudaMalloc`/`cudaFree` at ~175-300 microseconds per call (size-independent), the same order of magnitude as the whole measured training step. New `docs/architecture/cuda-memory-allocator.md` compares four candidate allocator designs against the actual trace and recommends an exact-size cache. **Decision: caching allocator justified**, deferred to a future milestone.

### M25 — Exact-size CUDA caching allocator
Implemented the allocator M24 recommended. New `forge/backend/cuda/allocator.py`: `CUDACachingAllocator`, a process-wide singleton owning `_free_blocks: dict[nbytes, list[ptr]]` (raw pointers only, never a `CUDAStorage`/`Tensor` reference). `CUDABackend._alloc()` delegates to `allocate()` (cache hit: pop and return, no driver call); `CUDAStorage.__del__()` delegates to `release()` (pushes onto the exact-size free list). Exact-size only -- no size-class rounding, block splitting, or coalescing, a deliberate scope limit. New public `forge.cuda.empty_cache()` returns cached (never active) blocks to the driver. Measured on the 940MX: 2.1-2.8x to over 100x speedup on isolated allocate/release depending on size; the real MNIST workload's mean iteration time dropped ~22%; real `cudaMalloc` calls collapsed from a projected ~2,240 to a measured 66. See `docs/architecture/cuda-backend.md`'s Caching Allocator section.

### M26 — CUDA execution and synchronization semantics
An audit, not a redesign: formally documented Forge's existing (already-correct) synchronous CUDA execution model before any future async work. Findings: Forge creates no CUDA streams -- every kernel launch and `cudaMemcpy` runs on the default stream, and every `CUDABackend` method already calls `cudaDeviceSynchronize()` before returning (established since M8), so execution is host-synchronous per operation despite individually-async CUDA calls. The M25 allocator's "safe to reuse immediately" design is formally justified by this same per-operation sync guarantee. New public `forge.cuda.synchronize()` thinly wraps the pre-existing `CUDABackend.synchronize()` -- no backend-level code changed. See `docs/architecture/cuda-backend.md`'s Execution and Synchronization Semantics section and `docs/architecture/cuda-memory-allocator.md`'s Synchronization Contract section.

### M27 — CUDA streams and asynchronous execution
Introduced real CUDA streams and an opt-in async execution mode on top of M26's formalized contract: `forge.cuda.Stream()`, `current_stream()`, `set_stream()`, `with forge.cuda.stream(s):` -- no public event API, stream priorities, pools, or CUDA Graphs. **Design decision: default-stream compatibility mode.** `current_stream() is None` (no active stream block) remains the exact M8-M26 host-synchronous behavior, byte-for-byte unchanged -- chosen specifically to avoid silently invalidating existing tests/user code that read a CUDA result back immediately with no explicit synchronization. Async execution (no per-op sync) is opt-in, only inside a stream block. **Cross-stream policy: fail clearly, not automatic dependency resolution** -- using a tensor last touched on one real stream from a different real stream raises `CUDAError` immediately. **Allocator change:** `CUDACachingAllocator` gained a third block state, *pending* -- a block released by a storage last used on a real stream is not immediately safe to reuse; release routes through `release_pending()`, which records a real internal `CUDAEvent`, and the block becomes reusable once that event completes. Autograd/optimizer/`Trainer`/persistence needed zero code changes. Measured overlap on the 940MX: default-stream baseline vs. two streams synced between them ~2.1x (from removed per-op sync alone); concurrent on both streams with a single final sync a further real ~1.14x from actual kernel overlap. See `docs/architecture/cuda-streams.md`.

### M28 — CUDA events and cross-stream dependencies
Replaced M27's "fail clearly on cross-stream Tensor use" policy with automatic GPU-side dependency insertion. `CUDABackend._stream_guard` now records a `cudaEvent` on a storage's producing stream and inserts `cudaStreamWaitEvent` on the consuming stream instead of raising, deduplicating multiple inputs sharing one producer stream into a single event. `last_stream` tracking (unchanged since M27) transitively handles multi-consumer chains with no extra per-Tensor metadata. Autograd, the optimizer, the allocator, and persistence needed zero code changes, since every CUDA compute path already ran through `_stream_guard`. Verified with a spy on `cudaDeviceSynchronize` that no host blocking is introduced.

### M29 — Async CUDA transfers and pinned memory
Added real pinned (page-locked) host memory (`forge.cuda.PinnedMemory`, direct uncached `cudaHostAlloc`/`cudaFreeHost`) and async H2D/D2H (`cudaMemcpyAsync`) behind an explicit `Tensor.to(device, non_blocking=True)` opt-in; the default `.to()` contract is unchanged. H2D requires an already-pinned source and raises rather than silently staging through a hidden pinned buffer. Host reads are synchronized lazily: `Tensor._data` became a property that synchronizes any pending transfer on first access. Cross-stream dependencies for async transfers reused M28's `_stream_guard` directly. **Hardware quirk documented, not fixed**: on the 940MX, an out-of-memory `cudaHostAlloc` can leave the process's CUDA context unable to serve subsequent small `cudaMalloc` calls -- the regression test runs in an isolated subprocess.

### M30 — Asynchronous DataLoader GPU prefetch
`forge.data.CUDAPrefetchLoader` (also `loader.prefetch(...)`) wraps an existing `DataLoader` unmodified, and `Trainer(..., prefetch=True)` transparently wraps whatever loader `fit()`/`evaluate()` receive. A single bounded background thread pulls CPU batches into a queue (backpressure via blocking `put()`); the calling thread stages each into pinned memory and submits async H2D on one dedicated transfer stream -- double buffering keeps exactly one batch staged ahead. Real overlap needs a real compute stream: `prefetch=True` creates one dedicated persistent compute stream for `fit()`/`evaluate()`'s duration (documented as superseding `cuda-streams.md`'s "Trainer remains synchronous" decision for this one opt-in path). The loader's one shuffle draw happens synchronously before the background thread starts, so no later draw races `Dropout`'s shared generator.

### M31 — Profile and optimize the async CUDA training pipeline
Built a non-synchronizing, event-based profiler (`benchmarks/pipeline_profile.py`) for the real M27-M30 pipeline. Finding: `CrossEntropyLoss` forward cost *more* wall-clock time than the entire M20 CNN's forward pass on a small tensor -- the composed implementation launched ~16 kernels total, and at this GPU's measured per-launch dispatch cost, launch overhead (not compute) explained it. Fused `Backend.cross_entropy`/`cross_entropy_backward` into 2 forward + 1 backward kernel launches, never materializing the one-hot matrix. Isolated op benchmark: forward ~2.5x faster, backward ~90x faster; end-to-end MNIST training step improved ~7%. Dependency/event overhead, allocator overhead, pinned-memory overhead, and prefetch queue depth were all profiled and found not to be bottlenecks -- none were touched, per the brief's "do not optimize for the sake of having an optimization." See `docs/performance/pipeline-profiling.md`.

### M32 — CUDA Conv2d backward optimization
M31 found `conv2d` backward at over half of CUDA training-step time. A dedicated profiler across 7 representative shapes found `dInput` (not `dWeight`, contradicting M21's MNIST-only finding) dominant at most shapes. Root cause: `k_conv2d_backward_input`'s validity resolution didn't depend on `Cout` but sat inside the `Cout` loop, causing `Cout`-fold redundant integer division per thread. Fix: hoist the resolution into small per-thread lookup tables built once before the loop. Isolated `dInput` kernel 1.5-1.8x faster; real MNIST CNN `conv2d` backward ~1.12x. `dWeight`'s own per-thread reduction was left as the next natural target, deliberately not pursued here.

### M33 — CUDA Conv2d dWeight cooperative reduction (investigated, rejected)
Tested two cooperative-reduction candidates for `dWeight`'s serial per-thread reduction: block-per-weight-element shared-memory tree reduction, and warp-per-weight-element `__shfl_down_sync` reduction. Both measured 3-4x *slower* than the existing per-thread kernel at every shape with many weight elements -- evidence the cost is dominated by sheer launch count across the 940MX's 3 SMs, not intra-group reduction overhead. Below the existing M21 threshold, the existing block-reduction path remained clearly faster, confirming that threshold is still correct. **Rejected** per the brief's explicit stop condition; both candidates were kept in `kernels.cu` as documented, tested, profiling-only code.

### M34 — CUDA Conv2d dWeight via im2col + existing tiled GEMM (accepted)
Built dWeight via im2col (two new gather kernels) feeding the existing, unmodified M11 tiled-GEMM kernel. 1.12-1.59x faster end-to-end than the existing kernel at shapes above a weight-element threshold, with modest peak-memory overhead; slower only at the smallest tested shape, where the GEMM's fixed tiling has little reuse benefit. **Accepted** as a minimal shape-based hybrid dispatch, reusing M21's existing threshold. MNIST's second conv layer conv2d backward improved ~1.44x.

### M35 — CUDA performance characterization and roofline-style analysis
A measurement-only milestone: built a roofline library and characterization scripts reusing Forge's own kernels as ceiling references. Measured practical 940MX ceilings: ~104.6 GFLOP/s compute (~11% of theoretical peak) and ~15.1 GB/s bandwidth (~94% of theoretical peak). Finding: in a real MNIST step, `conv2d` backward is the largest single component but only ~8% of its practical compute ceiling -- the clear top optimization-headroom candidate, well ahead of conv2d forward and matmul backward. GEMM itself already reaches 81-100%+ of the measured ceiling. D2H async transfers were found to pay a fresh `cudaHostAlloc` per call, making D2H submission far more expensive than H2D -- flagged as a future candidate, not fixed. M36 (dInput) was named as the next target. See `docs/performance/m35-roofline-characterization.md`.

### M36 — CUDA Conv2d dInput algorithmic optimization (accepted)
`nvcc -Xptxas -v` on the unmodified M32 dInput kernel found a per-thread **local-memory** stack frame -- real traffic invisible to the roofline model. Three candidates: **A** shared-memory grad_output row-tile reuse (**rejected** -- never beat baseline); **B** channel-fused work mapping, one thread per `(n,h,w)` holding all `Cin` accumulators in registers (**accepted** -- 1.0x-8.7x faster in isolation, zero stack frame confirmed); **C** warp-cooperative reduction over `Cout` (**rejected** -- 3-20x slower). Production dispatch now uses Candidate B whenever `Cin <= 16` (every Forge shape), falling back to the M32 kernel otherwise.

### M37 — CUDA Conv2d dWeight GEMM occupancy fix: split-K over existing buffers (accepted, modest)
Decomposing M34's im2col+GEMM pipeline found the GEMM's own launch geometry under-occupies the 940MX. **Candidates A/C** (fusing im2col/permute gathers directly into GEMM tile loads) -- **rejected**, recomputing gather indices every tile iteration cost more than it saved. **Candidate E** (keep M34's buffers, add a narrowly-scoped split-K GEMM kernel) -- **accepted**, 1.20-1.26x at low-occupancy production shapes, never regressed. An initial benchmark-harness bug had implied a much larger win; caught by cross-checking against real end-to-end timing before acceptance. A same-session, interleaved full-training-step A/B measured statistically indistinguishable from 1.0x -- reported honestly as a real isolated improvement too small to measure end-to-end.

### M38 — CUDA Conv2d dWeight im2col elimination: half-fused split-K GEMM (partial acceptance)
`nvcc -Xptxas -v` on `k_im2col_conv2d` found it thread-count-limited with zero spill -- its cost is genuine buffer read/write traffic. **Candidate B** (fuse only the `Xcol`/im2col operand's gather into the split-K GEMM's tile load): a clean, monotonic win at `blocks_y == 1` (1.30-1.44x) that flips to a real regression at `blocks_y >= 2` (0.68-0.93x). **Candidate C** (partial/tiled materialization) rejected analytically without implementation. **Partial acceptance**: dispatch now branches on `blocks_y` -- `== 1` calls Candidate B, `>= 2` keeps M37's kernel unchanged. Real MNIST conv2 layer (`blocks_y==1` regime) improved 1.164x at the full `conv2d_backward` level.

### M39 — CUDA Conv2d dWeight: im2col materialization optimization (shared-memory input-plane staging, accepted)
With M38 leaving `k_im2col_conv2d` itself dominant at `blocks_y >= 2` shapes, two candidates were tested. **Candidate A** (hoist index-decomposition redundancy via shared-memory broadcast, mirroring M32's dInput fix): **rejected** -- shape-dependent, regressing badly at small kernel sizes despite winning at larger ones, too inconsistent to dispatch safely. **Candidate B** (one block stages an entire input plane into shared memory once, serving all its im2col writes from shared memory): **accepted** -- won at every representative shape tested (1.05-1.96x), no measured regression. Full-pipeline validation (not just isolated im2col timing, per M37's lesson) measured 1.11-1.33x over the M37 baseline at `blocks_y >= 2` shapes. One real bug was caught and fixed during development: an early draft of Candidate A's host-table upload leaked a raw allocator pointer with no owning `CUDAStorage` (same bookkeeping mistake class as M33).

### M40 — Post-M39 CUDA bottleneck re-characterization (measurement-only, M41 target selected)
Fresh CUDA-event-based re-measurement confirmed dispatch correctness and found `dWeight`/`dInput` no longer have one uniform leader (alternates by `Cout`), with `dWeight` now the largest single component at MNIST's real shapes. Headline finding: `k_conv2d_forward` (unchanged since M15) reached only 10.7-18.0% of the practical compute ceiling, well below either backward kernel at the same FLOP count. Recommended M41: apply the already-validated im2col+GEMM technique to `k_conv2d_forward`.

### M41 — CUDA Conv2d forward: im2col + GEMM optimization (accepted)
Two GEMM-based forward candidates were built and measured against the baseline per-thread kernel; both win 1.06-2.85x above a large-FLOP threshold and regress below a small one (fixed launch overhead). `CUDABackend.conv2d` now dispatches by a FLOPs threshold to whichever candidate wins at the shape's `Cout`. Forward reached 43.2% of the compute ceiling (up from 17.0%) and became compute-bound at large shapes; MNIST's second conv layer measured 1.54x faster end to end. dInput/dWeight/`k_matmul` untouched.

### M42 — Fresh post-M41 CUDA bottleneck re-characterization (measurement-only, M43 target selected)
Confirmed M41's fix held (forward now 43.5-48.7% of ceiling). New finding: `dWeight`'s `blocks_y==1` split-K GEMM path (M38) reaches only ~22-25% of ceiling, about half the efficiency of forward's structurally similar half-fused GEMM -- the leading suspect is split-K's atomic-accumulation combine step. `dWeight` remained the single largest step component. Recommended M43: investigate a non-atomic split-K reduction strategy.

### M43 — CUDA dWeight `blocks_y==1` split-K reduction optimization (accepted)
Confirmed the atomic combine (not split count or register pressure) was the cause. Replaced it with a deterministic two-stage reduction (partial-GEMM writes to a buffer + a separate small reduce kernel) at the same split count -- 1.11-1.24x faster at the MNIST shape, never a regression, though the whole-step effect was honestly reported as within measurement noise (Amdahl dilution). A memory-leak bug in an early draft was caught by the new test suite and fixed before acceptance.

### M44 — Fresh post-M43 CUDA bottleneck re-characterization (measurement-only, M45 target selected)
Confirmed M43's win held and shrank `blocks_y==1`'s step share. With that path closed, the below-256-weight-element block-reduce kernel (unchanged since M21) became the single largest contributor while reaching only ~3% of the compute ceiling -- the worst efficiency measured to date, consistent with an occupancy-bound diagnosis. Recommended M45: a warp-shuffle cooperative reduction.

### M45 — CUDA dWeight below-256 warp-shuffle reduction (investigated, rejected)
Two warp-shuffle candidates were benchmarked against the production kernel. Rejected: at MNIST's real shape, gains were within noise and several swept shapes regressed. Root-cause correction to M44: the production kernel already launches 256 threads per weight element -- far more than either warp candidate -- so the path was never as parallelism-starved as M44's framing suggested. Production kernel left unchanged.

### M46 — CUDA dWeight below-256 grid-split reduction (investigated, rejected)
Tried the one remaining untried axis, grid-level parallelism. A real occupancy query found grid-splitting could not raise the 940MX's per-SM concurrent-block ceiling, which predicted no more than a marginal win -- confirmed: far short of the acceptance bar, with regressions at short reduction lengths. Also documented a methodology fix: an initial block-sequential timing harness produced an illusory large "win" that a properly interleaved rerun could not reproduce, due to the 940MX's clock/power state drifting over a sequential run (same class of error as M37, different mechanism). Production kernel unchanged.

### M47 — Fresh post-M46 CUDA bottleneck re-characterization (measurement-only, M48 target selected)
A three-way interleaved re-comparison of production against both M45's and M46's rejected candidates, plus a fresh occupancy re-query, reproduced M46's findings exactly and formally closed the below-256-dWeight thread: four independent angles (M21, M33, M45, M46) had now been tried without a milestone-clearing win. Also found that sustained multi-minute benchmarking sessions on the 940MX cause cumulative thermal/clock drift distinct from and larger than within-call drift -- every headline number in this report was re-verified or averaged across repeated trials in response. With below-256 dWeight set aside, no single component dominated the step anymore; recommended M48: target the M36 channel-fused dInput kernel's low-`Cin=1` regime. See `docs/performance/m47-bottleneck-recharacterization.md`.

### M48 — CUDA dInput low-Cin value assessment (accepted)
Before designing a candidate, confirmed `Cin=1` matters to exactly one real Forge shape (MNIST's first conv layer). Root cause was more nuanced than expected: a `Cin=1`-specialized kernel only modestly improved register usage/occupancy; the larger effect was eliminating redundant per-thread loop overhead from an unspecialized accumulator loop. A specialized kernel measured a 2.18-2.53x isolated-kernel speedup and ~1.16x end-to-end `conv2d_backward` speedup at the real shape. **Accepted** into production, dispatched only at `Cin<=1`; no regression at `Cin=2` or MNIST's second layer. See `docs/performance/m48-dinput-value-assessment.md`.

### M49 — Framework capability & value assessment (measurement/assessment-only; no implementation)
Surveyed optimizer coverage, NN layer/operator coverage, data-loading, serialization/checkpointing, and example coverage against Forge's own documented requirements/use-cases. **Conclusion: no implementation justified.** Every gap found (SGD momentum/LR scheduler, missing division/negation/power/sqrt/sigmoid/tanh/transpose/softmax/mean ops) was a previously-considered, deliberately deferred capability with no current real-workload impact -- two were already explicitly documented as intentional scope decisions elsewhere in the codebase. Data-loading and serialization already fully satisfied requirements; all seven use-cases already had a working demonstration. Recommended M50: make a concrete product decision (a second model family) rather than picking speculatively from this survey. See `docs/development/m49-capability-assessment.md`.

### M50 — Char-RNN: Forge's second model family
Selected a character-level vanilla RNN as Forge's second model family. Nearly everything needed (`Linear`, `CrossEntropyLoss`, `Adam`, dataset/persistence) already worked unmodified; weight sharing across a Python-level unroll loop was verified correct against the existing autograd engine before writing new code. One genuine blocker: `Tensor.tanh()`, added with full CPU/CUDA support following the established Tensor-primitive pattern, plus `nn.RNNCell`. Embeddings, LSTM/GRU gating, and multi-layer RNNs were deliberately rejected as unjustified without a driving consumer. Training recovered a synthetic corpus well below the untrained baseline, with confirmed CPU/CUDA parity. **Found but did not fix** (out of scope): a genuine self-deadlock in `CUDACachingAllocator.release()` (non-reentrant lock re-entered by a GC-triggered finalizer), diagnosed via `py-spy`; verification for this milestone worked around it via separate CPU-only/CUDA-only test runs.

### M51 — CUDA allocator reentrancy fix (`CUDACachingAllocator` self-deadlock)
Reproduced M50's deadlock deterministically, corrected the root-cause hypothesis (an unconditional `setdefault` list allocation while holding the lock, not the `any()` generator M50 suspected), and fixed it: `release()`/`release_pending()` now allocate nothing while the lock is held, and the lock became a `threading.RLock` as a deliberate, analyzed backstop for one remaining reentrant path. No performance regression detected. The full suite could now run as a single process again (no longer needing M50's CPU/CUDA split workaround).

### M52 — Product direction & third-workload assessment (assessment-only)
Evaluated five candidate next directions and selected a normalization-based CNN (`BatchNorm2d` added to the MNIST CNN) as the leading candidate, validating it directly against the real API via a throwaway probe. Found the genuine gap was an architectural concept, not an op: `Module` has no buffer mechanism (non-differentiable, device-moved, persisted, mode-aware state) -- a gap already flagged as deliberately deferred twice before (M16, M50). The probe confirmed CPU already supported BatchNorm's reduction/broadcast shapes (only `sqrt`/division missing); CUDA would need one dedicated fused kernel. Rejected: attention/transformer, autoencoder/extended char-RNN, generic CLI train/evaluate commands, SGD momentum/scheduler. No production code changed this milestone by design -- implementation deferred to M53.

### M53 — Module buffers and BatchNorm2d
Implemented M52's recommended capability in full: a non-differentiable, persistent, device-moved, mode-aware buffer mechanism on `Module` (explicit `register_buffer()`), two new general elementwise ops (`.sqrt()`, `__truediv__`), and `nn.BatchNorm2d`. CPU's forward composes entirely from general Tensor primitives with **no BatchNorm-specific backward rule** -- gradients fall out of ordinary autograd composition, verified against finite differences. CUDA, lacking general multi-axis reduction/broadcast, uses one dedicated fused kernel group instead. Serialization gained a buffers branch; `FORMAT_VERSION` bumped 1->2 as a deliberate, documented breaking change per ADR-003's existing policy. Added `examples/mnist/model.py::build_model_bn()` as the validation workload.

### M54 — Embedding lookup: fresh capability assessment and implementation
A fresh capability survey selected `nn.Embedding`/`Tensor.embedding_lookup()`: `char_rnn` (M50) had explicitly deferred this, and a direct probe measured the one-hot-plus-Linear workaround was 40x-3500x slower than a row-gather as vocabulary grew. Rejected: attention/transformer, binary classification, autoencoder, deeper RNNs, optimizer changes. Implemented on both CPU (NumPy fancy indexing + scatter-add backward) and CUDA (two new kernels, atomic add for repeated-index accumulation) as a genuine dual-backend primitive, unlike BatchNorm's CUDA-only fusion. Added `examples/word_rnn/` (`Embedding -> RNNCell -> Linear`), trained in lockstep on CPU and CUDA.

### M55 — Fresh post-M54 assessment: CUDA sequence-training was slower than CPU (engineering fix)
A fresh assessment measured a real, previously-unmeasured problem: CUDA trained `char_rnn`/`word_rnn` 1.5x-7.3x *slower* than CPU. Root-caused via `cProfile`: most of one epoch's wall-clock was spent in `CUDABackend._synchronize` -- the default CUDA stream's per-kernel-launch synchronize, paid by ~20-30 small kernel launches per unrolled training step at shapes too small to hide that fixed cost. Two fixes: (1) a fused CUDA `RNNCell` kernel (mirroring BatchNorm's CUDA-only-fused pattern); (2) the dominant fix -- running the example training loops' batch loop inside an explicit compute stream (`forge.cuda.stream()`, mirroring `Trainer`'s existing M27/M30 machinery), which neither example had ever adopted since neither uses `Trainer`. Combined: `word_rnn` moved from 1.7x slower than CPU to ~1.13x faster; `char_rnn` moved from 7.3x to 3.6x slower (still the wrong device for a model that small, but the gap narrowed sharply). See `docs/development/m55-post-m54-assessment.md`.

### M56 — Fresh post-M55 assessment: no production change warranted (assessment only)
Re-read every architecture document and prior milestone report; every previously-rejected candidate was re-examined and found still correctly rejected with no new evidence. One new candidate -- extracting `char_rnn`/`word_rnn`'s duplicated training-loop structure into a shared helper -- was seriously evaluated and rejected (only two consumers, no third sequence workload to validate an abstraction against). Assessment only, no production code changed.

### M57 — Fresh post-M56 assessment: no production change warranted (assessment only)
An independent fresh survey across six candidate areas reached the same conclusions M56 already reached, including a new candidate (sequence-to-sequence/encoder-decoder RNN) rejected because it would only recombine existing capability. Found and fixed two small repository-hygiene gaps in `examples/word_rnn/` (missing `.gitignore` entry, missing `README.md`) -- neither touches `forge/`, any public API, or any test. Fourth consecutive milestone to independently reach "no framework-capability change justified."

### M58 — Fresh post-M57 assessment: MNIST CUDA default-stream investigated, no bug found (assessment only)
Checked whether M55's default-CUDA-stream synchronize-overhead finding (RNN examples) also affected MNIST's `Trainer`-based CNN path. Measured directly: CUDA was already ~3.5x faster than CPU even without `prefetch=True`, which added only a further ~1.19x -- no bug, since MNIST's Conv2d/matmul kernels do far more arithmetic per launch than an RNN timestep, making the fixed per-launch synchronize cost negligible. Third consecutive assessment-only milestone.

### M59 — Vision reassessment: end the assessment-loop pattern; select tabular regression (UC2) as the next workload (strategic decision, no production change)
Stepped back from the ten-milestone narrow-capability-survey loop (M49-M58) to ask a project-level question: is Forge becoming what its vision document describes, or a pile of individually-justified additions? Finding: the code itself was coherent, but the project *surface* had real gaps -- Forge demonstrated only two of the vision's three named workload classes at production quality (regression, explicitly named as UC2, had only a bare unREADMEd verification script); the top-level onboarding surface (`README.md`) was stale; and five of the last ten milestones had been assessment-only with diminishing marginal signal. **Decision**: pursue tabular regression (UC2) as M60's objective, and adopt a permanent guardrail ending the assessment-loop-as-default pattern -- a fresh unscoped "survey and decide" milestone now requires a named external trigger, not automatic repetition.

### M60 — Tabular regression example (`examples/regression`, UC2)
Built Forge's third vision-named workload family to the same production standard as `mnist`/`char_rnn`/`word_rnn`. A deterministic synthetic tabular dataset (8 continuous features, linear+interaction+quadratic target plus noise, one deliberate distractor feature) trains a plain `Sequential` MLP through `Trainer.fit()` with zero `Tensor`/`Backend`/`nn` changes needed. CPU training reduced MSE close to the dataset's noise floor; CUDA matched within floating-point tolerance but ran ~3.3x *slower* than CPU at this small-batch scale (reported, not chased, per M59's performance policy).

### M61 — Framework readiness and developer experience (documentation + one discoverability fix, no new ML capability)
With three vision-driven workload families complete, addressed the stale top-level onboarding surface: `README.md` was a 5-line stub, and `forge/__init__.py`'s docstring narrated only milestones 1-26. One real API gap found and fixed: `forge.cuda.is_cuda_available()` didn't exist, forcing callers to reach into an internal-looking path -- fixed via re-export. Rewrote `README.md` and the package docstring, added `examples/README.md` as a central index, added `tests/test_smoke.py`, and added a CPU-only GitHub Actions CI workflow -- an evidence-based decision since most test files are CPU-only or skip CUDA cleanly. All four major examples were actually re-run end-to-end to verify documentation accuracy.

### M62 — `nn.Conv1d`/`nn.MaxPool1d`: 1D temporal convolution, plus a real waveform-classification workload
Found a genuine gap in UC1 coverage: Forge had no way to express 1D/temporal convolution. Added `nn.Conv1d`/`nn.MaxPool1d` by reshaping `(N,C,L)` to a dummy `(N,C,1,L)` and dispatching to the existing, already-optimized `Conv2d`/`MaxPool2d` machinery -- the same "compose from an existing op, no new Backend/CUDA code" convention `nn.Flatten` established. Added `examples/waveform_classification/`. **Incidental fix**: found and fixed a pre-existing bug where `examples/regression/train.py --device cuda` crashed because `CUDABackend.reshape` never supported `-1` shape inference (unlike CPU's NumPy-delegated version).

### M63 — Convolutional autoencoder: `nn.UpsampleNearest2d` and Forge's first unsupervised-reconstruction workload
Selected a convolutional autoencoder as the first workload whose training signal is its own input. A genuine blocker was discovered by implementation: every prior architecture only ever shrinks a spatial feature map; the decoder needed the opposite. Added `nn.UpsampleNearest2d`, backed by a new dual-backend primitive pair -- composing it with `Conv2d` (upsample-then-convolve) is a deliberate standard choice avoiding transposed convolution's checkerboard artifacts. `examples/autoencoder/` reuses `examples/mnist/dataset.py`'s real MNIST data and trains through `Trainer.fit()` completely unmodified. A bonus check found same-digit test images cluster in latent space despite fully unsupervised training. CUDA trained substantially faster than CPU here (unlike `regression`/`waveform_classification`).

### M64 — U-Net-style image segmentation: Forge's first dense-prediction workload, zero new framework capability
Attempted the workload against Forge's existing capabilities before assuming any gap -- building and training a `Conv2d`/`MaxPool2d`/`UpsampleNearest2d` U-Net-style model succeeded immediately with no missing method. `examples/segmentation/` is the first Forge image example generating fully synthetic data rather than downloading or reusing MNIST. IoU rose from a trivial baseline to 0.99 on both CPU/CUDA. One candidate gap (true U-Net skip connections, needing a `concat` primitive that doesn't exist) was explicitly considered and rejected as unjustified speculation. Zero new production capability required.

### M65 — Reproducible training/experiment workflow: `examples/regression`, zero `forge/` change, one real gap found and closed
Turned `examples/regression` into a repeatable configure->seed->train->record->checkpoint->resume->evaluate->compare workflow. **One genuine, execution-proven gap**: a resumed run with `shuffle=True` re-seeded a fresh DataLoader generator instead of continuing the interrupted shuffle stream, measured as a real divergence versus continuous training -- root-caused and fixed entirely via the existing checkpoint `extra` mechanism (no new API), closing the divergence to exactly 0.0. Added `experiment.py` (versioned JSON run records) and `compare.py` (plain-text diff of two runs).

### M66 — Residual CNN workload: `examples/resnet`, zero `forge/` change
Investigated whether Forge's existing `Module`/`Conv2d`/`BatchNorm2d`/serialization could express and train a small ResNet-style network with branch+shortcut addition; a finite-difference probe confirmed `Tensor.__add__`'s existing gradient-accumulation mechanism already handles a residual branch/shortcut correctly. Built `ResidualBlock` and `ResNetMNIST` entirely in `examples/resnet/` -- the first nested custom-`Module`-inside-custom-`Module` tree registered for persistence -- with zero `forge/` changes. Trained on real MNIST with genuine CPU/CUDA parity, confirming checkpoint/resume and save/load work correctly through a deeply nested module tree.

### M67 — `nn.LSTMCell`: closing a measured `RNNCell` vanishing-gradient gap, plus `examples/long_range_recall`
Re-opened the LSTM/GRU direction earlier assessment milestones (M52/M54-M57) had deferred for "no consumer," this time backed by direct measurement: a gradient-norm probe against `RNNCell` showed the gradient reaching the first timestep underflowing to exactly 0.0 in float32 at long sequence lengths -- a real, measured limitation. Added `Tensor.sigmoid()` (CPU + CUDA, following M50's `tanh` precedent) and `nn.LSTMCell` (composed from 8 existing `Linear` layers plus `+`/`*`/`sigmoid`/`tanh`, forget-gate bias initialized `+1.0` per Jozefowicz et al. 2015); a combined single-`Linear` gate projection was considered and rejected since it needs a Tensor slicing primitive Forge doesn't have. Built `examples/long_range_recall/` supporting both `RNNCell` and `LSTMCell` via `--cell`. Honest finding: end-to-end trainability at long sequence lengths did not reliably converge for either cell within tested budgets, a more nuanced result than the clean gradient-norm story alone suggests.

### M68 — `forge.predict()`: a standalone post-training inference path
A project-level review of the full train->evaluate->save->load chain found the final "predict" step had no dedicated API -- six of Forge's nine examples had each independently hand-rolled the identical `no_grad()`+forward+`.to("cpu").numpy()` sequence. Added `predict(model, inputs, device=None) -> Tensor` (`forge/training/inference.py`) as a free function (deliberately not a `Trainer` method, which would force constructing an unneeded `Loss`/`Optimizer`, and not `Module.predict()`, which would blur `Trainer`'s own orchestration boundary). Retrofitted all six affected examples.

### M69 — `forge.data.ImageFolder`: directory-based image classification, Forge's first real-world data-ingestion layer
Added `ImageFolder(root, transform=None, target_transform=None, extensions=...)` -- a `Dataset` discovering `(image, label)` samples from a `root/class_x/*.jpg` tree, Pillow-decoded. Built `examples/image_folder_classification/` end-to-end. Honest finding: the first working version did not generalize (validation accuracy stuck at chance) because a small 2-conv network couldn't learn a color-polarity-invariant edge detector from few samples; fixed by constraining the generator's color polarity and adding `BatchNorm2d` + `Dropout(0.3)`, both pre-existing `forge.nn` layers.

### M70 — `forge.data.transforms.Resize`: making mixed-resolution `ImageFolder` datasets batchable
Closed M69's documented limitation that every image under one `ImageFolder` root had to share `(H,W)`. Added `Resize(size)` -- an ordinary `Transform` using Pillow's bilinear filter, no new abstraction, no `Tensor.resize()`, no CUDA kernel. Extended `image_folder_classification` to generate mixed-resolution images and resize during training. Honest finding: accuracy dropped versus M69's uniform-resolution result because the mixed-resolution task is genuinely harder and `Resize` distorts aspect ratio (aspect-preserving resize was out of scope) -- not a regression.

### M71 — Persisted preprocessing: `save_model(..., preprocessing=...)` / `load_preprocessing()`
Closed the gap that a saved model carried no record of the preprocessing its inputs must go through. Added `forge/serialization/transforms.py`: a `register_transform()` registry mirroring the existing `Module` persistence registry (`Lambda` deliberately never registered, since it has no safe serialized representation) plus `serialize_transform()`/`deserialize_transform()`. `save_model()` gained an optional `preprocessing=` kwarg; `load_preprocessing()` reconstructs it independently. No `FORMAT_VERSION` bump. `image_folder_classification/train.py` switched its one `Lambda` pixel-scale step to the equivalent, serializable `Normalize(mean=0.0, std=255.0)`, and gained `infer.py`, a genuinely standalone fresh-process inference script.

### M72 — Class-Label Metadata: `save_model(..., classes=...)` / `interpret_classification()` / `forge model predict`
Closed the next blocker to normal model use: a saved `.forge` file couldn't answer "what classes does this model predict." Added `save_model(model, path, classes=[...])`, saving an ordered class-name list as a new optional metadata key (same pattern as preprocessing, no `FORMAT_VERSION` bump). Added `forge.training.interpret_classification(output, classes)`, turning `predict()`'s raw `Tensor` into a `ClassificationPrediction` (label, index, confidence) via a numerically stable host-side softmax. Added the first CLI prediction command, `forge model predict MODEL --image IMAGE`. In passing, fixed `forge model convert` silently dropping `preprocessing`/`classes` metadata across a device conversion.

### M73 — Reusable Training Workflow: `start_training_session()`
Found an identical ~10-line "load checkpoint + Trainer + resume(), else build model + Trainer" branch duplicated across all seven checkpoint-capable examples -- and that only 2 of the 7 carried M65's `DataLoader`-shuffle resume-equivalence fix, meaning the other five silently carried the same latent resume divergence bug. Added `forge.training.start_training_session()`/`TrainingSession` (`forge/training/session.py`), automatically folding/restoring the `DataLoader` RNG state on every checkpoint, generalizing M65's fix to every consumer for free.

### M74 — `forge.data.sequential_split`
Found that `examples/regression/dataset.py` and `examples/waveform_classification/dataset.py` each independently hand-rolled identical contiguous-block array-slicing to split an i.i.d. dataset. Added `forge.data.sequential_split(dataset, lengths) -> list[Subset]` -- `random_split` without the permutation. `segmentation`'s dataset was correctly left alone since its train/test come from two independent RNG streams, not one array to slice.

### M75 — `forge.training.generate_sequence()`
Found `examples/char_rnn/train.py::generate()` and `examples/word_rnn/train.py::generate()` were structurally identical autoregressive sampling loops. Added `forge.training.generate_sequence(model, seed, encode, decode, length, device=None, rng=None)` -- the shared loop, extracted once, with eval-mode/`no_grad()`/mode-restoration exactly like `predict()` and host-side softmax + `rng.choice` sampling (never greedy argmax).

### M76 — `forge.data.save_image()`: rendering image-shaped model output
Found that `examples/autoencoder` (reconstruction) and `examples/segmentation` (predicted mask) each produced an image-shaped `Tensor` with no rendering step -- only scalar metrics were ever printed. Added `forge.data.save_image(tensor, path)` -- a `(C,H,W)` Tensor with `C` in `(1,3)`, scaled to `[0,255]` uint8 and written via Pillow; a terminal, non-differentiable reporting operation, not a `Transform`/`Dataset`.

### M77 — Portable artifacts for the MNIST family: preprocessing/classes persistence + fresh-process inference
Found the M71/M72 preprocessing+classes mechanism was never used outside `image_folder_classification`. A second, more serious finding: neither of the two examples with custom-registered Module trees ever saved (`autoencoder`, `resnet`) had ever been `load_model()`-ed by a process that hadn't already imported their own `model.py` -- a real, permanent artifact-portability constraint documented (not fixed) going forward. Fixed the `Lambda` gap across `mnist`/`autoencoder`/`resnet` and added `examples/mnist/infer.py`, Forge's flagship example's first standalone fresh-process inference script.

### M78 — First complete developer workflow: `save_and_verify()`
Found all ten examples' `train.py` scripts independently hand-wrote the identical "save the model, reload it fresh, `predict()` on both, assert `numpy.allclose`" round trip. Added `forge.training.save_and_verify(model, path, sample, device=None, preprocessing=None, classes=None, atol=1e-5) -> Module` -- composes `save_model()`/`load_model()`/`predict()`, raising `forge.PersistenceError` instead of a bare `assert`, and returning the freshly reloaded `Module`. ### M100 — First-class early stopping: `EarlyStopping`, best-model restoration
M98 measured a real overfitting curve on `examples/tabular_diabetes` (validation loss bottoms around epoch 9-14 of 60); M99's `TrainingResult` exposed that after the fact but explicitly named "Forge has no early stopping" as the resulting limitation. Added `forge.training.EarlyStopping` (`forge/training/early_stopping.py`) -- `monitor` (default `"val_loss"`, or `"val_<metric name>"`), `patience`, `min_delta`, `restore_best`, `mode` (`"min"`/`"max"`, not inferred) -- consumed by `Trainer.fit(..., early_stopping=...)` and forwarded through `forge.train()`/`forge.train_and_save()`; requires validation data, raising `TrainerError` immediately otherwise. `fit()` stops after the epoch that exhausts `patience` consecutive non-improving validation results (every requested epoch still runs without `early_stopping`, unchanged), and, when `restore_best=True`, restores the model's parameters/buffers in place to the best-scoring epoch's in-memory snapshot before returning -- reusing `Module.named_parameters()`/`named_buffers()` plus each Tensor's own backend `to_numpy()`/`from_array()` transfer primitives rather than a second serialization system; no optimizer state is snapshotted or restored (documented boundary -- `train()`/`train_and_save()` never owned a checkpoint/optimizer-continuation contract to begin with). `TrainingHistory` gained `stopped_early`/`best_epoch`/`best_monitored_value`/`monitored_quantity` (defaulting to `False`/`None`/`None`/`None`, so every pre-M100 caller is unaffected); `TrainingResult`/`TrainAndSaveResult` copy them through. `train_and_save()` needed no extra logic to save the restored model: `fit()` restores it in place before `train()` returns, so `save_and_verify()` already sees the corrected state. Retrofitted `examples/tabular_diabetes/train.py` with an opt-in `--early-stopping`/`--patience`/`--min-delta` (default off, so the existing default workflow is bit-for-bit unchanged) -- a real `--epochs 60 --seed 0` run genuinely stopped at epoch 12 (best epoch 7, best val_loss 0.5204), reproduced identically on CPU and CUDA, and measurably reduced test loss (0.5858 -> 0.5115) versus the fixed 60-epoch run at the same seed, though test accuracy matched (72.1%) at this sample size. Verified from a genuinely fresh process and from a built wheel installed into a clean venv outside the repo. New `tests/test_early_stopping.py` (24 tests: config validation, patience/min_delta off-by-one semantics, best-epoch restoration proven against an independently-trained reference run, `restore_best=False`, real `val_accuracy` monitoring, determinism, `train_and_save()` integration) and `tests/test_early_stopping_cuda.py` (3 hardware-gated tests, restoration proven on real `CUDAStorage`).

### M107 — Real-world developer experience: `train_image_classifier()`
A product/DX milestone, not another framework-capability check: a real dogfooding run (`sandbox/t1_cat_dog/train.py`, ~25,000-image `sandbox/petimages` cat/dog dataset, predating this milestone) proved Forge's *framework* already handles a realistic image-classification workload end-to-end, but exposed that reaching that result required a developer to hand-assemble every stage: build `Resize`+`Normalize` twice (once for `ImageFolder(transform=...)`, again for `train_and_save(preprocessing=...)`, nothing keeping the two in sync), hand-derive a CNN's flattened `Linear` input size for the chosen resolution, compute split sizes from a fraction, hand-pick a batched `sample` Tensor purely to satisfy `save_and_verify()`'s calling convention, and -- the most serious gap -- reach past `ImageFolder`'s public surface into the underscore-prefixed `_load_image()` and mutate `.samples` directly just to skip 2 corrupt JPEGs out of 25,000, since `DataLoader` has no per-sample error recovery and one bad file would otherwise abort an entire run partway through. ### M113 — First-class saved-artifact evaluation: `ArtifactPredictor.evaluate()`
Implements the fourth item of the M112 1.x surface. `forge.load_predictor(path).evaluate(X, y)` scores a loaded artifact on held-out labeled data through the *prediction* path -- raw input -> `InputSchema` check -> persisted `preprocessing` -> model -> metrics -- so the caller never rebuilds `Normalize`/`ReplaceValue`/`Resize` (the M97 trap: `Trainer.evaluate()` on raw Pima rows gave 37.0% for a 72.1% artifact). No second prediction path: each batch runs through the existing `_predict_tensor_core()` (numeric) or the same decode+preprocess step `_classify_image_core()` uses (image); nothing reloads the artifact, no format change, no new `Metric` class, `Trainer` untouched. **Supported tasks:** `tabular_classification` and `regression` (`X` array/list/`Tensor`), and `classification` (image; `X` is an `ImageFolder`-layout directory, labels = folder names matched to `predictor.classes` *by name*); `segmentation`/`sequence` raise `DataError` (no evaluation semantics yet). **Results** (frozen, exported from `forge.training`): `ClassificationEvaluationResult` (`task, samples, loss, accuracy, baseline_accuracy, classes, confusion_matrix` [read-only, rows = true, columns = predicted, artifact class order], `precision, recall, support`) and `RegressionEvaluationResult` (`task, samples, loss, mse, mae, baseline_mse`), each with a `metrics` dict on the existing `accuracy`/`mse`/`mae` keys. Zero division is defined (`0.0`, never NaN/warning); baselines are computed on the *evaluated* data (Pima holdout 62.3%, not the 65.1% full-dataset share). Metrics are computed once over concatenated outputs, so `batch_size` only bounds memory. Invalid input (missing/mismatched/unknown `y`, wrong feature count or rank, NaN/Inf in `X`/`y`/output, a model-rejected shape, bad `batch_size`) raises `DataError`; a classifier with no persisted `classes` or a class count that disagrees with the model output raises `PersistenceError`. **Decision vs M112:** M112 sec. 6.3 said "no `loss` (not persisted)", but the M113 brief requires it; `loss` is `CrossEntropyLoss`/`MSELoss` -- the only losses Forge has for these tasks -- via the existing classes. **Validation:** Pima holdout, 154 rows: accuracy 72.08% vs 62.34% baseline, loss 0.5858, confusion `[[78,18],[25,33]]`, precision `(0.757, 0.647)`, recall `(0.813, 0.569)` -- identical to `examples/tabular_diabetes/evaluate.py` (left unchanged as the independent oracle; accuracy/baseline to 1e-12, confusion exact, loss/precision/recall against a separate NumPy computation); two fresh processes importing nothing from `examples/` agree with each other and this process exactly; CPU vs CUDA (940MX) agree (confusion/accuracy exact, loss within 1e-4). Regression validated on a controlled hand-computed fixture only; real-dataset validation deferred to M114. The bundled `models/image_classifier` also evaluates on a synthetic folder and matches per-image `predict()`. **Tests:** 43 new (39 CPU in `tests/test_artifact_evaluation.py`, 4 CUDA in `tests/test_artifact_evaluation_cuda.py`); a mutation check (dropping the preprocessing) fails 11 of them. Docs: `persistence.md`, `README.md`, `examples/tabular_diabetes/README.md`, `Trainer.evaluate()` docstring. Full suite: **2,845/2,845 passed, 0 skipped** (599s, CUDA present). **Found, not fixed (pre-existing):** a ragged nested list passed to `predict()` leaks a raw NumPy `ValueError` from `Tensor()` (`_coerce_numeric_input`); `evaluate()` wraps it in `DataError` locally, `predict()` left as is. **Deferred:** `evaluate.py` still hand-composes rather than delegating; segmentation/sequence evaluation; a `forge model evaluate` CLI (no natural CSV contract).
